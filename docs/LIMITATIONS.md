# Limitations

The development scorecard scores the draft from approach 1, the default. That run does not call a model. `tools/evaluate.py` on the development corpus is 12 of 12 when the mock is on `127.0.0.1` with a temporary state file. Nothing below is a claim about a hidden corpus, a live bank, or a measured invoice.

## What the program will not do

- It does not approve. Approval is the separate `approve` command in `tools/runtime.py`. There is no approve route on the mock. Saving reviewer feedback does not approve or decline.
- Code under `src/` and `scripts/` does not read `dataset.json`. The lint gate fails a `src/` file that names that file. `scripts/` was searched and does not name it.
- Approach 1 is the default. The rules write classification, routing, facts, deadline, missing information, and policy ids, and no model is called. `--approach 2` asks the configured model (`LLM_MODEL` in `.env`, currently `claude-haiku-5-5`) after the rules, on the cases the rules leave open. With no model client, or an empty key, the rules class stays (`rules_only`). `--approach 3` asks Jev first, then Clef when Jev is missing or the call fails, then the configured model. An ambiguous Jev or Clef answer goes to manual review and does not call the configured model. A ranker class that matches the rules is kept. A disagreement asks the configured model, and that class stands only when it matches the rules or the ranker. When no ranker returns a class, the configured model is asked, or the rules class stays when that client is missing (`rules_only`, or `model_failed` when a ranker call failed). `--approach ab` assigns a case from a seeded hash. `--shadow` writes an audit for every approach and leaves the draft on the selected approach. `dispute-copilot compare` and `make compare` run the three approaches on one fetched transaction list.
- A model may be asked only when the rules class is ambiguous with no conflict, or unauthorized from complaint wording while authorization is not supplied. A labeled denial, a conflict, and a rules class of unsupported, duplicate, or service are not sent. After a proposal, unauthorized is kept only when the label is not supplied or denied. A confirmed label contradicts an unauthorized proposal, so the class does not stand and the route is `manual_review`. Duplicate and service are kept only when the label is confirmed or not supplied. A denied label never reaches a model, and any other class with that label is a hard failure.
- A duplicate stands only when the already-fetched transactions contain two charges with the same merchant id, amount, and currency. Otherwise the class does not stand, the deadline is cleared, and the route is `manual_review`. If the transaction read is unavailable, the class stays `duplicate_charge`, the route is `manual_review`, and the deadline is still calculated. This check runs on every approach, including the rules.
- When the final class is unauthorized and authorization was not supplied, the missing fields include authorization confirmation. A labeled denial does not add that field. A service class with authorization not supplied lists authorization confirmation first.
- The ranker threshold in `config/rules/classifier.yaml` is a placeholder of `0.70`. Jev cost is unpriced. `config/rules/cost.yaml` prices `claude-haiku-4-5` at 1.00 USD per million input tokens and 5.00 USD per million output tokens. `claude-haiku-5-5` has no row, so that id is recorded as `no price configured for claude-haiku-5-5` with no USD figure.
- The checklist critic runs only when `FEATURE_LLM_REVIEW=block`. It can fail the checklist. It is not given the scored fields to rewrite, and it does not approve.
- Classification audits under `submissions/classification/` and the mirror under `reports/` do not store the complaint. The comparison page does not show it. The review page is the only page that shows the original complaint, after the narrative. That page escapes the text and runs the redactor on the finished HTML. A restricted value returns 403 and withholds the page. Reviewer login is phase 2. The feedback form stores a typed name, a category, a note, and whether the closed Haiku block was opened.
- The mock listen address in `create_server` is `127.0.0.1`. Health was requested on that address. `ss` was not installed here, so a second look at the socket table was not taken.
- `src/dispute_copilot/mcp_server.py` speaks stdio only. It does not take a port. `run_case` and `run_all` accept `approach` (`1`, `2`, `3`, `ab`, or omit for approach 1) and `shadow`. There is no compare tool and no approve, reject, or reset operation. The module does not read the fixture file. The `mcp` library is an optional extra. Without it, `uv sync --locked` still installs the copilot and the server module exits 1. Complaint text and evidence quotes returned by `get_draft` are marked untrusted data. A passing checklist through `agent_review` does not approve the case. `create_record` still stops on the existing gate. The saved draft is not a resource URI, because that library attaches the requested URI to a resource error.
- `dispute-copilot dashboard` is read-only. Served, it binds `127.0.0.1` and answers GET `/`, `/index.html`, `/compare`, `/compare.html`, and `/health`. POST, PUT, PATCH, and DELETE return 405. `--export` writes the status HTML and a sibling comparison page and does not listen. The page does not approve. Per approach, the comparison page shows the wrong-label rate, the auto-routed-but-wrong rate, the manual-review rate, Haiku cost per case, and latency p95, plus an agreement matrix and disagreeing case ids. Auto-routed but wrong counts only a route of `ready_for_review`. Cost per case divides Haiku list-price USD by cases run. Jev is unpriced. A wrong-label sample or an auto-routed sample under `comparison.min_sample` (30) is marked too small to conclude. Token prices in `config/rules/cost.yaml` are USD per million tokens. A listed model is an estimate from list price. A model with no entry is named. Compute cost is `estimate, unmeasured` unless `compute.usd` is set. Human review state is `unmeasured` without `audit.json`. A place appears on the status page only when a saved run has it. An export of `evidence/week10/reports` was opened in headless Chrome. The log filter for `CARD-D08` left 16 of 189 lines visible. The page was not served from the Azure app.

## Known gaps

- A customer reference or other restricted value inside a cited quote is masked, and the case continues, when readable words remain. If the quote would be only the mask, that quote is dropped and routing becomes manual review. Masking a quote does not recompute the class or the transaction facts. A masked quote is no longer an exact excerpt, so `citations_valid` would fail for that case. The twelve development complaints keep the reference on a labeled line, which is not cited, so the 12 of 12 result does not exercise masking.
- Card detection keeps 13–19 digits that pass a Luhn check, with or without single spaces or dashes. A value that is only a `span_id`, `trace_id`, `parent_id`, or `run_id` hex token is left as-is, including a 16-digit token that would pass Luhn, so an identifier is not rewritten. IBAN-shaped text is masked when the checksum matches. Account numbers are masked when a label (`account`, `acct`, or `a/c`) sits in front of 8–17 digits. Bare digit strings are not treated as accounts, because that would collide with other ids. Email addresses use a conventional form. Phone detection covers a leading `+` and 8–15 digits, one spaced international form, and a 3-3-4 national form. Other national layouts can pass through.
- Instruction-like text in a complaint, attachment, follow-up, or merchant payload is not allowed to change a scored field by itself. The trace records `injection_detected` with the case id, source id, and pattern category. The raw sentence is not written to the log or the trace. The checklist note names the categories. A pass of that checklist still does not approve. Approach 2 or 3 can still send a redacted complaint to the model on an eligible case. Leave `CLASSIFIER_APPROACH` unset, or set it to `1`, to keep classification on the rules.
- Editing the local draft file after approval does not make `create-record` fail. The create step posts the draft stored on the mock at submit time, so the local edit is not the body that is saved. Editing that stored draft after approval, while leaving its hash unchanged, makes `create-record` exit 2 with `record was not created (status 403)`, and no record is written. The gate was not changed. A stricter rule that also fails the local-file edit is not implemented.
- `good_case_rate` counts drafted case spans whose `duration_ms` is at or under `latency_target_ms` (2000) divided by all case spans. It does not read the route, and it is not the classification latency on the comparison page. `config/rules/slo.yaml` uses that same sentence. A fast draft whose route is manual review still counts as good. See `docs/SLO.md`.
- `reports/dev.json` scores the development gold file only. It does not score narrative quality, approval, shadow approaches, or a second corpus.
- Citation support counts a quote only when the source id exists and the quote appears in that source text. It does not judge semantic support. Markdown ids use the files. Payload ids use the texts from `tools/source_index.py`. `src/` does not open the fixture file.
- Guardrail events record that an existing protection fired. They do not approve, and they do not set a scored field. A passing approval gate emits no `guardrail.approval` event.

## Not verified here

- Image build, compose, and any sign-in to the running Azure app. `docker` was not installed in this session, and this session could not reach `<subscription>`. The names in ADR-33 were supplied, not queried. Cost cells are unmeasured. Job `azure` and `.github/workflows/azure-deploy.yml` were not run against the replica. No `az containerapp exec`, `az login`, registry push, or `az containerapp update` was issued here. The side-ledger rehearsal in `tests/unit/test_azure_live.py` did run: a seeded demo review stayed `pending`, the demo calls row stayed at 7, and evaluate was 12 of 12.
- A socket listing that the mock refused non-loopback binds, beyond the fixed address in code and the health call to `127.0.0.1`.
- The critic, approach 2, approach 3, and the ranker with a live key. No key was used in the recorded development run. Default runs stay on approach 1 with the checklist judge off. Empty `JEV_BASE_URL` or `JEV_API_KEY` skips Jev. Empty `CLEF_API_KEY` or `CLEF_ACCOUNT_ID` skips Clef.
- Phone and account shapes outside the patterns above. No extra examples were supplied.
- Data other than `data/dev`.
- Reviewer login. The review page has no login. That work is phase 2.

## What is still open

Reviewer login is phase 2. Approval stays the human command in `tools/runtime.py`. Restricted values stay masked before they are logged, traced, or placed in a prompt. Classification audits and the comparison page do not store the complaint.

Worth doing without loosening those gates: decide whether a local draft edit after approval should fail `create-record`; add phone or account patterns only from examples the team provides; run the image build in an environment that has a container engine.
